Our VMS is now connected, but a working screen is not enough to prove that the system is reliable. Before deployment, we need to test it at different levels. We will start small with one business rule, then test the connected backend through its APIs, and finally test the complete application from the user's point of view. Each test answers a different question and helps us find problems before the VMS goes live. We begin with the duplicate vehicle number rule. This is a focused unit test, because we are testing one piece of business behavior instead of running the whole application. The repository is mocked, so we do not need the real SQL database. We test two simple cases. An existing vehicle number should be rejected, while a new vehicle number should be accepted. If this test fails, we know the problem is inside this specific business rule. To understand why the test matters, temporarily break the duplicate rule and run the test again. This time, the test should fail. That failure proves that our test is actually protecting the behavior we care about. We can then give anti-gravity the exact failure, ask it to identify the cause, and apply the smallest correction. Restore the proper rule, rerun the test, and confirm that it passes again. Next, we move from one isolated rule to the connected backend. Start Spring Boot and the SQL database. Then, run the complete CRUD scenario. Create a vehicle, retrieve it, update it, verify the changed value, delete it, and confirm that it is gone. We also test error cases such as duplicate vehicle numbers, missing required fields, and invalid IDs. Unlike the unit test, this check proves that the backend layers and the real database work correctly together. Finally, we perform an end-to-end test. This time, we use the application exactly as a real user would. Start the full local stack, log in through Flutter, register a vehicle, confirm it appears in the list, update a field, and then delete the record. We also try an error path by submitting a duplicate vehicle number or incomplete data. The important point is that the entire journey now travels through Flutter, the REST API, Spring Boot, and SWILL. No mock vehicle data should be involved. By the end of this section, we have three different levels of confidence. The unit test tells us whether one important business rule behaves correctly. The API test tells us whether the backend components and SQL database work together. And the end-to-end test tells us whether a real user can complete the full VMS journey through the actual interface. If any step fails, we identify the failing layer, make the smallest safe fix, and rerun the test. Once these checks pass, the VMS is ready for the next stage, deployment.
