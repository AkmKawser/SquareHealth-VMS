So far, our VMS has a working front-end, but the vehicle data is still temporary. Now we move behind the screen and build the part that makes the application real. Spring Boot will handle requests and business rules, while SQL will store the information permanently. We will keep the back-end completely separate from the Flutter project. By the end of this demo, our back-end will be able to receive vehicle data, validate it, save it, and return it through REST APIs. We begin with our separate VMS back-end repository. The project uses Java and Spring Boot, with the basic dependencies needed for web requests, database access, and validation. Open the generated project in Antigravity and run the Spring Boot application. At this stage, we are not building vehicle features yet. We simply want to confirm that the back-end starts successfully, listens on its local port, and remains completely independent from our Flutter front-end. Next, we connect Spring Boot to the SQL database. This is the moment when our back-end gains permanent memory. Configure the database driver, the JPA settings, and the connection details. Sensitive values, such as usernames and passwords, should stay outside the source code and must not be committed to GitHub. Then start Spring Boot again. If the application starts successfully with the database configured, we know the connection is working and we are ready to store real vehicle information. Now we can build the actual vehicle back-end. We define the fields that belong to a vehicle, including vehicle number, company, type, brand, model, and status. Antigravity can help create the entity, repository, service, validation, and exception handling structure. But one business rule is especially important. Vehicle number must be unique. If someone tries to create the same vehicle twice, the service layer should reject it with a clear error instead of creating duplicate data. Once the business logic is ready, we expose it through REST APIs. These APIs become the communication point between our future Flutter client and the back-end. We create endpoints for adding a vehicle, reading vehicles, updating a record, and deleting it. The API should return clear responses, useful validation errors, and the correct HTTP status codes. At this stage, we test the APIs independently. Flutter is still not connected, and that is intentional. Before connecting Flutter, we prove that the back-end can stand on its own. Create a vehicle through the API and confirm that the record is stored in SQL. Fetch the vehicle list and make sure the saved data comes back correctly. Then test update and delete. Finally, try creating the same vehicle number again and confirm that the back-end rejects it. If Spring Boot runs, SQL stores the data, the CRUD APIs respond correctly, and the duplicate rule works, our back-end is ready. In the next section, we will replace Flutter's mock data with this real API data and connect the two projects together.
