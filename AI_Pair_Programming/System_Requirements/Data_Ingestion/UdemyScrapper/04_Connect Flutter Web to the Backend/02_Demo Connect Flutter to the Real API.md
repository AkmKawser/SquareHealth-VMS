Up to this point, we have built two separate projects. Flutter gives us the VMS interface, while Spring Boot and SQL handle the business logic and permanent data. But the front end is still working with mock information. Now we connect these two sides. Flutter will send requests to the Spring Boot REST API. Spring Boot will process them. SQL will store the data. And the result will come back to the interface. The first change is replacing the mock vehicle repository with the real API. We keep the existing Flutter screens, but the data now comes from Spring Boot instead of temporary front-end records. Antigravity can help us create a small reusable API layer and request and response models that match the backend contract. We also add proper loading, success, empty, and error states. The API base URL should remain configurable, so we can use a local address now and the production URL later. Let's follow one real action. A user fills in the register vehicle form and presses save. Flutter sends that information to the backend API. Spring Boot receives the request, applies validation and business rules, and stores the vehicle in SQL. The API then returns a response, and Flutter updates the vehicle list. This is the key change in this section. The screen may look almost the same, but the information is now coming from the real application stack. Next, we connect the existing Flutter login screen to the backend authentication flow. The frontend should follow the authentication contract already defined by Spring Boot, rather than inventing a different process. Valid credentials should allow the user to continue into the VMS, while invalid credentials should produce a clear message. Vehicle operations should also be protected, so an unauthenticated user cannot simply call the backend directly. And throughout this process, passwords should never be written into logs or stored insecurely. Now we connect the complete vehicle workflow. The vehicle list loads records from the backend. Register vehicle sends a create request. Editing a vehicle sends an update request, and delete calls the backend only after the user confirms the action. The UI should change only after the backend confirms success, so the screen always matches the database. We also deliberately test an error case by submitting a duplicate vehicle number. Spring Boot should reject it, and Flutter should show the backend error clearly instead of failing silently. Before moving into the testing section, we run the full local journey from beginning to end. Start the database. Start Spring Boot. And run Flutter web. Login with valid credentials. Register a vehicle. Confirm that it appears in the list. Update one field. And then delete the record. Check the SQL database as you go, so the data matches what you see on screen. Finally, confirm that duplicate and validation errors are handled properly, and that no mock vehicle data is involved anymore. At this point, our two separate projects are working together as one connected VMS. Next, we will test that system more deliberately.
